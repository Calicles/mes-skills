# Design de solution

## Règles communes : à lire avant toute action

**Jamais de code sans fiche validée** : porte 1 (fiche, planches dans `ressources/planches/`, « je valide » explicite) avant tout code livré ; porte 2 (rendu final validé) avant toute fusion.
Avant de commencer, lire dans `references/regles-communes.md` la section « Les deux portes, version générique (projets hors jeu) » : elle fait foi (les autres sections ne s'appliquent pas à ce skill).
Ci-dessous, seulement ce qui est propre à ce skill.

**Dans ce skill** : le design ne passe jamais le relais au code sans que la personne sache que la réalisation commencera par la porte 1 (fiche et planches validées). Le message à coller dans Claude Code le rappelle.

## Quand utiliser ce skill

Après le cadrage d'un projet (skill `cadrage-projet-perso`), pour passer du "quoi/pourquoi" au "comment" : concevoir la solution elle-même — concept, fonctionnalités, parcours d'usage, structure, et choix techniques à haut niveau (projets avec code) ou forme des livrables (projets sans code).

Ce skill est le prolongement direct du cadrage, mais dans un mode de pensée opposé : le cadrage résiste activement à la solution pour bien cerner le problème ; ce skill part au contraire du principe que le problème est déjà clair et qu'il faut maintenant explorer des solutions avant de choisir. Ne pas mélanger les deux logiques dans la même conversation sans transition claire.

Comme pour le cadrage, tous les projets sont personnels par défaut dans cet espace : pas de vocabulaire de gestion de projet corporate, sauf si la personne précise explicitement que c'est un projet professionnel.

## Emplacement de référence du projet (règle commune à tout le workflow)

Un projet = UN dépôt GitHub privé = UN seul endroit pour tout ce qui le concerne (documents de référence, livrables, ressources, et code s'il y en a), quelle que soit la surface utilisée (Claude, Cowork, Claude Code, Claude AI) et que le projet nécessite du code ou non. Même structure dans les deux cas.

- **Dépôt** : un dépôt privé par projet, sur le compte GitHub personnel de la personne (vérifier avec `gh api user --jq .login`), avec le topic `projet-perso` et un topic de type `avec-code` ou `sans-code` (`gh repo list --topic projet-perso` pour retrouver le projet).
- **Structure** : `docs/` = uniquement les documents de référence (`cadrage.md`, `design.md`, `wireframe.md` au singulier, `wireframe.html`, plus `docs/game-design/` pour un jeu vidéo (un fichier par métier : `experience-joueur.md`, `gameplay.md`, `level-design.md`, `personnages.md`, `architecture.md`, `mobilier-decor.md`), `journal-decisions.md` (les décisions datées) et `fiche-<étape>.md` (les fiches de réalisation)) ; `livrables/` = ce que le projet produit (si un livrable vit dans un Doc ou un artifact claude.ai, y ranger son export, sa source ou son lien dans `livrables/liens.md`) ; `ressources/` = recherches, sources, notes ; `src/` = le code, projets avec code uniquement ; `CLAUDE.md` à la racine, toujours (le modèle est dans le skill `cadrage-projet-perso`) ; `README.md` d'une ligne.
- **Aucune autre copie de référence** : ni dossier local, ni espace cloud seul, ni mémoire, ni Projet Claude. Un lien vers le dépôt est possible, jamais une copie qui pourrait diverger.
- **Lire / écrire** : cloner le dépôt (ou `git pull`) avant de lire ; après chaque écriture, commit avec un message clair puis `git push`.
- **Si GitHub est inaccessible** depuis la surface en cours : le dire clairement, ne pas enregistrer ailleurs en silence, garder le contenu dans la conversation et proposer de le pousser dès que possible.

## Prérequis : le cadrage, validé élément par élément

Ce skill exige qu'un cadrage existe. Retrouver le dépôt du projet (`gh repo list --topic projet-perso`, ou le nom donné par la personne), le cloner ou le mettre à jour, lire `CLAUDE.md` (notamment la ligne `Type`) puis chercher `docs/cadrage.md`. Si le dépôt n'existe pas mais que le cadrage traîne ailleurs (dossier local, mémoire, Projet Claude, conversation), proposer de le rapatrier une seule fois avec le skill `migration-projet-perso`, avant de continuer. S'il n'existe aucun cadrage, ne pas designer à l'aveugle : le dire clairement et proposer de faire d'abord le cadrage (skill `cadrage-projet-perso`) avant de continuer.

Une fois le `docs/cadrage.md` trouvé, le lire en entier. Puis le faire valider par la personne en très petits lots, un élément à la fois, jamais plusieurs éléments regroupés dans le même message :

1. Envoyer uniquement le vrai besoin (tel que challengé au cadrage), rien d'autre. Attendre la validation.
2. Puis, dans un nouveau message, uniquement la cible. Attendre la validation.
3. Puis uniquement le contexte d'usage. Attendre la validation.
4. Puis uniquement les contraintes. Attendre la validation.
5. Puis uniquement le périmètre v1 (inclus/exclu). Attendre la validation.
6. Puis uniquement les inspirations retenues au benchmark. Attendre la validation.

Chaque message de cette séquence ne contient QUE l'élément du moment, formulé en une ou deux phrases courtes — pas de récapitulatif des éléments déjà validés, pas d'anticipation sur l'élément suivant, et surtout jamais la moindre piste de solution ou question sur les moments d'usage tant que tous les éléments du cadrage n'ont pas été validés un par un. Si la personne corrige un élément, l'ajuster avant de passer au suivant plutôt que de continuer avec une base périmée (et mettre à jour `docs/cadrage.md` dans le dépôt si la correction change le cadrage). Ne pas redemander ces éléments sous forme de questions ouvertes — ils sont déjà tranchés au cadrage, il s'agit seulement de les confirmer un par un.

## Principe général

Diverger avant de converger : ne pas se jeter sur la première idée de solution qui vient. Explorer plusieurs pistes distinctes, pas de simples variantes d'une même idée, avant de choisir avec la personne.

Les pistes se construisent à partir d'une interview, pas d'une intuition solitaire : ne jamais inventer seul des pistes de solution à partir du seul cadrage. Entre "identifier les moments d'usage" et "proposer des pistes", il y a toujours une étape d'interview de la personne sur chaque moment (voir Étape 1 ci-dessous). Sauter cette interview et deviner à la place de la personne est la cause la plus fréquente d'un design qui "patauge" : la personne finit par devoir elle-même corriger ou compléter des pistes mal calées, alors que ses préférences auraient pu être recueillies dès le départ.

Le même risque existe une marche plus bas, au niveau des fonctionnalités : une fonctionnalité validée comme titre ("gérer la liste de mots") peut cacher des mécanismes concrets non tranchés (comment on ajoute un mot ? comment on corrige la liste ensuite ?). Les laisser de côté jusqu'à la réalisation ou le wireframing produit le même patauge que sauter l'interview : la personne se retrouve à devoir inventer ces mécanismes dans l'urgence, plus tard, alors qu'ils font partie du design de la solution. C'est pourquoi chaque fonctionnalité se traite en plusieurs temps — diverger, converger, puis décomposer en fonctions concrètes (voir Étape 4).

Ce mouvement diverger/converger ne se joue pas qu'une fois, au niveau du concept global (étapes 2-3) : il se répète, en plus petit, à chaque fonctionnalité qui a un vrai choix à faire (étape 4a-4b), et encore plus petit si un mécanisme de cette fonctionnalité cache lui-même plusieurs façons plausibles de le réaliser (étape 4c). Ne pas confondre ce mini-diamant avec une simple ébauche qu'on ajuste après coup : diverger, c'est présenter plusieurs façons distinctes de faire, pas une seule idée qu'on affine. À l'inverse, ne pas fabriquer de fausses alternatives quand une option s'impose déjà clairement (parce que le concept retenu la contient, ou qu'il n'existe réellement qu'une façon sensée de faire) — le signaler explicitement est toujours préférable à une divergence artificielle, qui serait elle-même une forme de complexité non justifiée.

Garde-fou permanent, symétrique à celui du cadrage : au cadrage on évitait de sauter trop vite à une solution ; ici, le risque inversé est de partir dans une solution plus complexe que ce que le vrai besoin justifie. À chaque choix (fonctionnalité, fonction, technique, structure), se demander si sa complexité est justifiée par un élément réel du cadrage ou de l'interview, ou si c'est un réflexe ("parce que c'est plus propre", "parce que c'est comme ça qu'on fait d'habitude", "parce que ce serait plus scalable") sans besoin réel derrière — surtout pour un projet personnel qui n'a pas vocation à grandir sans limite. Quand c'est le cas, le dire franchement et proposer l'option plus simple.

Règle de découpage valable pour tout le skill, pas seulement le rappel du cadrage : un message = un seul lot, le plus petit possible pour rester vérifiable d'un coup d'œil, et on attend la réaction de la personne avant de passer au lot suivant. Dès qu'un message mélange deux éléments qui pourraient chacun être validés séparément (par exemple deux éléments du cadrage, ou un récapitulatif suivi d'une nouvelle question, ou deux décisions distinctes à trancher à l'intérieur d'une même liste — comme deux fonctionnalités différentes, ou deux fonctions d'une même fonctionnalité, à l'étape 4), le découper en plusieurs messages plutôt que de les empiler, même si cela transforme une liste en plusieurs messages successifs. Les étapes qui demandent une vue d'ensemble pour arbitrer (comparer les pistes de solution entre elles à l'étape 2, ou comparer les options d'une fonctionnalité ou d'un mécanisme à l'étape 4, par exemple) restent groupées, parce que la comparaison est le but même de l'étape — mais tout ce qui est de la validation ou de la confirmation d'un fait déjà établi, ou une décision à prendre, se découpe au maximum, y compris quand cela concerne plusieurs éléments d'une même liste (comme la liste des fonctionnalités clés, ou la liste des fonctions d'une fonctionnalité, où chacune se valide séparément plutôt qu'en bloc). Ne jamais regrouper dans un même message la divergence ou la convergence de deux fonctionnalités différentes, ni celles de deux mécanismes différents d'une même fonctionnalité : chaque diverger/converger reste son propre mini-lot.

## La maïeutique (l'esprit de tout le design)

Les questions de ce skill ne sont pas un formulaire à remplir : elles servent à faire exprimer à la personne, aussi loin que possible, ce qu'elle imagine, et à laisser émerger ce qu'elle n'avait pas encore formulé, pour produire ce qui lui ressemble et ce qu'attendent vraiment ceux qui s'en serviront. Claude ne tranche rien seul ; ses propositions servent à affiner ce que la personne a exprimé, jamais à le remplacer.

- **Ouvrir avant de proposer** — avant chaque série de pistes ou d'options (le concept à l'étape 2, chaque fonctionnalité à l'étape 4a, chaque mécanisme à l'étape 4c), demander d'abord ce que la personne imagine : « comment vois-tu ça ? raconte-moi ce que tu fais à ce moment-là ». Les pistes se construisent ensuite à partir de sa réponse. Reformuler ce qui a été dit (« si je te suis bien… ») et relancer : pourquoi ? qu'est-ce que ça évoque ? ça ressemble à quoi que tu connais ? raconte-moi le moment où… Creuser chaque mot vague jusqu'à ce que la personne dise « oui, c'est exactement ça ». Les options (2 ou 3, en cartes avec le skill `poser-questions-en-cards` s'il est installé) ne viennent qu'**ensuite**, en partant de ses mots, pour préciser ou pour l'aider si elle sèche ; la recommandation vient en dernier, avec sa raison en une phrase.
- **Suivre son fil** — l'ordre des questions à l'intérieur de chaque étape est un repère, pas un script (les étapes elles-mêmes gardent leur enchaînement) : si la personne part ailleurs, la suivre, puis revenir aux thèmes qui n'ont pas été abordés avant de conclure. Ne pas reposer ce qui est déjà dit ou tranché, mais signaler une contradiction.
- **La voix des utilisateurs** — dès que d'autres personnes que la personne elle-même se serviront du projet (famille, enfants, amis, joueurs), recueillir ce qu'elle sait d'eux : ce qu'ils aiment, ce qu'ils font aujourd'hui, ce qu'ils ont dit, réclamé, ignoré, et qui aime quoi. Proposer **3 ou 4 questions à leur poser** (courtes et concrètes, adaptées à leur âge), puis reprendre avec leurs réponses. Signaler quand ce que la personne imagine et ce que les utilisateurs semblent attendre s'écartent, et en faire une question.
- **Ce qui émerge** — noter toute idée apparue en route, même hors sujet, et demander régulièrement « qu'est-ce qui te vient d'autre ? ». Relire ces idées à la fin de chaque grand bloc ; pour chacune, la personne décide : maintenant, plus tard (notée dans le document, section des idées pour plus tard), ou abandonnée.
- **Finir par la scène** — à l'étape 5, raconter le parcours d'usage comme une scène vécue par la personne et ses utilisateurs, puis demander : « est-ce ce que tu imaginais ? qu'est-ce qui manque ? ». Chaque écart relance l'interview avant d'écrire le document.

Ces principes s'ajoutent aux règles ci-dessous (un lot court par message, challenge, garde-fous) sans les remplacer : une question ouverte reste une seule question, et un message reste un seul lot.

## Étapes

0. **Identifier tous les moments d'usage à couvrir** — une fois tous les éléments du cadrage validés un par un, et avant toute autre chose, relire le cadrage.md et lister explicitement tous les moments d'usage distincts que la solution devra couvrir (y compris ceux des autres utilisateurs, à partir de la voix des utilisateurs recueillie au cadrage), pas seulement le moment principal le plus évident. Un projet a souvent plusieurs moments différents : l'usage récurrent principal, mais aussi des moments périphériques nécessaires comme faire entrer une information dans le système (une liste, des données de départ), suivre ou mettre à jour quelque chose dans le temps, ou gérer un cas exceptionnel. Chercher ces moments dans le contexte d'usage, le périmètre et les contraintes du cadrage. Présenter cette liste à la personne dans un message court (une liste à puces suffit), pour vérifier qu'aucun moment important n'est oublié.
1. **Interviewer la personne sur chaque moment d'usage, avant de proposer quoi que ce soit** — pour chaque moment validé à l'étape 0, un à la fois, poser des questions ouvertes plutôt que d'imaginer seul comment le résoudre : est-ce qu'elle a déjà une idée en tête pour ce moment précis ? Qu'est-ce qui compterait le plus pour elle à ce moment-là (rapidité, fiabilité, simplicité, autre chose) ? A-t-elle déjà vu, utilisé ou imaginé quelque chose — ailleurs, dans une autre app, dans sa vie quotidienne — qui l'inspire ou qu'elle veut éviter pour ce moment ? Qu'est-ce qui la frustrerait si ce moment était mal géré ? Même esprit que les questions du cadrage sur les besoins non exprimés (mises en situation concrètes plutôt qu'abstraites), mais appliqué ici à l'imagination de la solution plutôt qu'à la définition du besoin. Ne pas sauter cette étape même quand un moment paraît simple ou évident : c'est précisément quand elle est sautée que les pistes proposées ensuite ratent des préférences importantes de la personne, qui ressortent alors après coup, en réaction aux pistes, plutôt que d'avoir nourri les pistes dès le départ — c'est ce qui donne l'impression de "patauger". Ne passer à l'étape suivante qu'une fois tous les moments interviewés.
2. **Diverger : plusieurs pistes de solution** — à partir du vrai besoin, des inspirations retenues au benchmark, et surtout de tout ce qui est sorti de l'interview à l'étape 1, proposer 2 à 4 pistes de solution clairement distinctes, construites à partir de ces éléments concrets — jamais inventées indépendamment de l'interview. Si la personne a déjà exprimé une préférence ou une idée précise pendant l'interview pour un moment donné, l'intégrer directement dans les pistes plutôt que de proposer autre chose et attendre qu'elle corrige. Pour chaque piste, dire explicitement comment elle traite chacun des moments d'usage identifiés — si une piste ne traite pas un moment, le signaler explicitement plutôt que de le laisser implicite. Indiquer aussi brièvement les avantages et les limites de chaque piste au regard des contraintes du cadrage. Ne pas orienter artificiellement vers une seule piste évidente : donner un vrai choix. Cette étape reste groupée (toutes les pistes dans le même message) puisque la comparaison entre elles est le but de l'étape.
3. **Converger : choisir un concept** — discuter les pistes avec la personne et l'aider à choisir, en challengeant si elle penche vers l'option la plus complexe alors qu'une option plus simple couvrirait déjà le vrai besoin (et tous les moments d'usage). Si elle préfère quand même l'option plus complexe, demander pourquoi avant d'accepter : la raison peut révéler un vrai besoin non encore nommé (comme la crainte de perdre le fil d'un historique), qui justifie alors la complexité — ou être un simple réflexe à challenger. Décrire le concept retenu en une phrase claire, et noter explicitement pourquoi il répond au vrai besoin.
4. **Fonctionnalités clés : pour chacune, diverger puis converger avant de décomposer en fonctions concrètes, une fonctionnalité à la fois** — d'abord identifier, pour soi, les fonctionnalités de la v1, chacune reliée explicitement à un élément précis du cadrage ou de l'interview (le vrai besoin, un besoin non exprimé, une contrainte, une inspiration du benchmark, une préférence exprimée à l'étape 1, ou un moment d'usage identifié à l'étape 0). Puis traiter chaque fonctionnalité l'une après l'autre, en trois temps :
   - **a. Diverger** — pour cette fonctionnalité seule, demander d'abord, en une question ouverte, comment la personne l'imagine (voir "La maïeutique") ; puis proposer 2 à 3 façons distinctes de la réaliser (pas de simples variantes d'une même idée), construites à partir du concept retenu à l'étape 3, de l'interview de l'étape 1 et des inspirations du benchmark — jamais inventées dans le vide. Si un mécanisme évident domine largement et qu'il n'existe pas d'alternative sensée (par exemple parce que le concept retenu à l'étape 3 l'impose déjà), le dire explicitement plutôt que d'inventer 2-3 options artificielles pour la forme, et passer directement à l'étape b avec cette option unique. Sinon, présenter les options dans un même message (la comparaison est le but, comme à l'étape 2), avec pour chacune son lien explicite au cadrage/interview et ses avantages/limites au regard des contraintes. Si une fonctionnalité envisagée ne se relie à rien de précis, le signaler comme candidate au hors-périmètre au moment même de la présenter, plutôt que de l'inclure par réflexe, et proposer de la mettre explicitement en "pas pour la v1".
   - **b. Converger** — discuter les options avec la personne et l'aider à choisir, dans un nouveau message dédié à cette seule décision. Même réflexe anti-complexité qu'à l'étape 3 : si elle penche vers l'option la plus riche alors qu'une option plus simple couvrirait déjà le besoin derrière cette fonctionnalité, le signaler et demander pourquoi avant d'accepter. Noter en une phrase l'option retenue et pourquoi.
   - **c. Décomposer en fonctions nécessaires** — une fois l'option retenue, se demander si elle cache plusieurs mécanismes concrets distincts nécessaires pour qu'elle fonctionne vraiment. Exemple type : une fonctionnalité "gérer la liste de mots" n'est pas une action unique — elle implique au moins une fonction d'ajout (et il faut alors trancher comment on ajoute : saisie, photo, import...) et une fonction de modification de ce qui a été ajouté (corriger, supprimer, compléter). Si de tels mécanismes existent, les lister puis les traiter un par un, chacun dans son propre message. Pour chaque mécanisme, si plusieurs façons plausibles de le réaliser existent, refaire le même mini-cycle diverger/converger qu'aux points a et b, mais à l'échelle de ce seul mécanisme : présenter les options dans un message, obtenir un choix dans le message suivant, avant de passer au mécanisme suivant. Si un mécanisme n'a au contraire qu'une seule façon sensée de le réaliser, le dire explicitement plutôt que de fabriquer une divergence artificielle, et ne demander que sa validation. Si la fonctionnalité entière est déjà atomique (une seule action, sans mécanisme caché), le dire explicitement plutôt que d'inventer une décomposition artificielle.
   Ne passer à la fonctionnalité suivante qu'une fois son option choisie et toutes ses fonctions (et leurs éventuelles sous-divergences) validées. Le but : que les mécanismes concrets (comment on ajoute, comment on modifie, comment on saisit...) soient non seulement tranchés mais explorés avant d'être tranchés, ici, au design, plutôt que découverts et choisis à la va-vite plus tard pendant le wireframing ou la réalisation — c'est le même risque de "patauger" que sauter l'interview de l'étape 1, appliqué au niveau des fonctionnalités et de leurs mécanismes.
5. **Parcours d'usage principal** — dérouler le scénario concret d'utilisation, du déclencheur jusqu'à la fin d'usage, dans le contexte réel défini au cadrage (support, fréquence, état d'esprit). Éviter un parcours abstrait — utiliser une mise en situation concrète ("un mardi soir, sur le téléphone, la personne fait X..."). Si d'autres moments d'usage identifiés à l'étape 0 ont leur propre parcours distinct, les décrire aussi brièvement, pas seulement le moment principal. Raconter ce parcours comme une scène, puis demander : « est-ce ce que tu imaginais ? qu'est-ce qui manque ? » ; chaque écart relance l'étape concernée.
6. **Structure / organisation** — quand c'est pertinent, décrire comment l'information ou le contenu est organisé (catégories, champs, étapes, sections) en texte structuré, sans maquette visuelle.
7. **Choix techniques à haut niveau (projet avec code) ou forme des livrables (projet sans code)** — selon la ligne `Type` de `CLAUDE.md` :
   - *Avec code* : uniquement si pertinent pour ce projet (langage, outil, plateforme, format de stockage). Le code sera écrit par Claude Code dans le dépôt du projet : ne pas hésiter à choisir ce qui est le plus simple à construire, déployer et maintenir dans ce cadre. Toujours proposer d'abord le choix le plus simple compatible avec les contraintes du cadrage (budget, temps disponible), et n'introduire une option plus lourde que si elle répond à une contrainte précise — pas par principe de "bonne pratique" générique. Appliquer le même réflexe aux moments d'usage secondaires : si un moment périphérique peut se traiter en dehors de la solution principale plutôt que d'être intégré dedans, et que ça reste tout aussi simple pour la personne, proposer cette option plus légère.
   - *Sans code* : écrire "choix techniques : sans objet (projet sans code)" et ne rien inventer. À la place, trancher la forme des livrables : quels livrables, dans quel format (document, tableur, page...), sur quel outil, avec quel rythme de mise à jour, et où ils sont rangés dans le dépôt (`livrables/`).
8. **Périmètre confirmé** — relire le périmètre v1 défini au cadrage à la lumière des choix de design, et l'ajuster si le design a fait apparaître des éléments à exclure ou reconsidérer.
9. **Definition of done** — critères concrets et vérifiables permettant de dire "la v1 est faite", reliés au résultat attendu défini au cadrage.
10. **Première étape concrète de réalisation** — affiner, à la lumière du design retenu, la première étape déjà identifiée au cadrage : quelle est la plus petite chose à construire, produire ou tester en premier. Pour un projet avec code, la formuler de façon assez précise pour qu'elle puisse être donnée telle quelle à Claude Code.

## À la fin

Produire un document `design.md` structuré reprenant : le concept retenu (et brièvement les autres pistes explorées et pourquoi elles n'ont pas été retenues), les moments d'usage identifiés et ce que l'interview a fait ressortir pour chacun, les fonctionnalités clés avec leur lien explicite au cadrage, l'option retenue pour chacune et, quand une vraie divergence a eu lieu, les autres options envisagées et pourquoi elles n'ont pas été retenues, et pour chacune les fonctions concrètes qui la composent quand elle en a (par exemple : ajout, modification) avec les mêmes alternatives envisagées et non retenues quand un mécanisme en a fait l'objet, le parcours d'usage principal (et les parcours secondaires s'il y en a), la structure/organisation, les choix techniques et pourquoi (ou "sans objet" et la forme des livrables pour un projet sans code), le périmètre confirmé, la definition of done, la première étape, et les idées notées pour plus tard.

Relire le document avec la personne pour confirmer, puis l'enregistrer dans `docs/design.md` du dépôt GitHub du projet, à côté de `docs/cadrage.md` (commit + push, règle "Emplacement de référence"), pour qu'il fasse partie du contexte de référence du projet au même titre que le cadrage, depuis n'importe quelle surface.

### Mettre à jour CLAUDE.md et passer le relais

Dans tous les cas, mettre à jour le `CLAUDE.md` à la racine du dépôt (le créer s'il n'existe pas, avec le modèle du skill `cadrage-projet-perso`) : ligne `Type` confirmée, liste des documents de référence à jour, variante de la règle 2 adaptée au type. Commit et push.

- **Projet avec code** : dire à la personne, en une ou deux phrases, que le design est enregistré dans le dépôt `<compte>/<nom>` et que la suite se fait dans Claude Code sur ce dépôt (en ouvrant une session Claude Code sur ce dépôt), avec un premier message à coller : "Lis CLAUDE.md et docs/, puis prépare la première étape de docs/design.md : commence par la porte 1 (fiche et planches à me faire valider), sans coder avant mon accord." Proposer de passer d'abord aux wireframes (`wireframing-perso`) si le projet a une interface qui mérite d'être pensée avant de coder, ou, si la personne préfère aller vite, de passer directement à Claude Code : vite, mais après la porte 1 (la réalisation commence toujours par la fiche et les planches validées). Ne pas commencer à coder dans cette conversation, sauf demande explicite de la personne, et jamais avant la porte 1.
- **Projet sans code** : pas de relais vers Claude Code. Dire à la personne que le design est enregistré dans le dépôt, que la suite consiste à produire les livrables définis au design (rangés dans `livrables/`, depuis n'importe quelle surface), et que si un besoin de code apparaît un jour, le passage en code se fait sans rien déplacer (skill `evolution-projet-perso`, section "Passage en code"). Proposer les wireframes seulement si un livrable a une dimension d'interface ou de mise en page à penser.

Proposer de mettre à jour ce document si des choix de design changent en cours de réalisation, plutôt que de le considérer figé : toute mise à jour se fait dans `docs/design.md` du dépôt, avec commit et push.
